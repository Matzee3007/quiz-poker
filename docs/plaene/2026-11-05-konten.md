# Plan: Konten mit Einladungscode

**Ziel:** Eingeladene legen mit einem einmal gültigen Code ein Konto an, melden sich mit E-Mail und Passwort an und ab, setzen ein vergessenes Passwort über einen Link des Betreibers neu und können ihr Konto löschen.

**Vorgehen:** Erst eine Messung im echten Betrieb bei Cloudflare, die den Plan stoppen kann. Danach Server und Betriebsbefehle testgetrieben, dann Mock und Oberfläche, zuletzt Pflichtseiten, Sicherheitsprüfungen und Veröffentlichung. Better Auth übernimmt Anmeldung und Sitzungen, das Hashing läuft in einem Durable Object. Registrieren und Passwort-Link sind eigene Wege, weil es dafür keine E-Mails gibt.

**Technik:** Better Auth 1.7.17, Cloudflare D1, Durable Objects, Svelte 5, Vitest 4. Neue Abhängigkeit nur `better-auth`, von [[projects/quiz-poker/docs/adr/0005-konten-mit-einladung-ohne-e-mail|ADR 0005]] gedeckt.

**Anforderung:** Schritt 2 von Phase 3 in [[projects/quiz-poker/docs/Projektvision|Projektvision]], Abschnitt „Quiz-Sammlung“, [[projects/quiz-poker/docs/adr/0005-konten-mit-einladung-ohne-e-mail|ADR 0005]].

**Umfang:** Nur Konten. Quizze speichern (Schritt 3) und öffentliche Quizze (Schritt 4) bekommen eigene Pläne. Das Löschen eines Quiz und das Mitlöschen der Quizze eines Kontos kommen deshalb erst mit Schritt 3. Bis dahin bringt ein Konto online noch keinen Nutzen, Spielraum und Einmal-Quiz bleiben ohne Konto.

## Feste Vorgaben

- Registrierung nur mit Einladungscode, gültig bis zur Nutzung. Kein E-Mail-Versand, die Adresse wird nicht geprüft.
- Anmeldung gilt 30 Tage ohne Verlängerung, Passwörter haben 8 bis 128 Zeichen.
- Link zum Zurücksetzen gilt 24 Stunden und einmal.
- Außer E-Mail und Passwort-Hash keine persönlichen Daten: Better Auth verlangt einen Namen, dort steht fest `Quiz-Master`. Telemetrie von Better Auth aus. Sitzungen speichern weder IP-Adresse noch Browserkennung (`ipAddress`, `userAgent` bleiben leer, Test in Aufgabe 4).
- Einladungscodes und Links liegen nur als SHA-256-Hash in D1.
- Das Hashing läuft nur im Durable Object `Passwortrechner`, nie im Worker selbst.
- Neu in diesem Plan, zusätzlich zur Klärung: höchstens 10 Anmeldeversuche pro Minute je IP-Adresse (Header `cf-connecting-ip`), gezählt in D1. Better Auth zählt dabei alle Versuche, nicht nur die falschen. Eigene Konto-Anfragen höchstens 4 KiB.
- Spielraum und Einmal-Quiz funktionieren weiter ohne Konto, die vorhandenen Tests bleiben unverändert grün.
- Veröffentlicht wird erst, wenn die kurzen Datenschutzhinweise fertig sind und der Cloudflare Security Audit Skill gelaufen ist. Kein Impressum, keine Namen und keine Anschrift auf der Seite ([[projects/quiz-poker/docs/adr/0006-kein-impressum|ADR 0006]]). Der PR bekommt `/code-review` und `/security-review`.
- Vor jedem Commit `npm run check`. Vitest bleibt bei Version 4. Oberfläche auf Deutsch, Stil C, PC-Breite.

## Schnittstelle zwischen Gerät und Server

```text
POST /api/konto/registrieren { code, email, passwort }  → 201 + Sitzungs-Cookie | 403 einladung-ungueltig | 409 email-vergeben | 422 passwort-laenge, ungueltige-email, ungueltige-nachricht
POST /api/konto/passwort-neu { token, passwort }        → 204 | 403 link-ungueltig | 422 passwort-laenge, ungueltige-nachricht
/api/auth/*                                             → Better Auth: sign-in/email, sign-out, get-session, delete-user
POST /api/auth/sign-up/email                            → 404, abgeschaltet
```

Beide eigenen Wege antworten zusätzlich mit 403 `fremde-herkunft`, wenn der Header `Origin` nicht zur eigenen Adresse passt, und mit 413 `anfrage-zu-gross` über 4 KiB.

## Prüf-Schwerpunkte

1. Jemand ruft die Registrierung von Better Auth direkt auf und umgeht die Einladung: 404, kein Konto (Aufgabe 3).
2. Zwei Anfragen nutzen gleichzeitig denselben Code: genau ein Konto entsteht (Aufgabe 4).
3. Die Registrierung scheitert an einer vergebenen Adresse oder einem zu kurzen Passwort: Der Code bleibt gültig (Aufgabe 4).
4. Ein Link wird zweimal benutzt oder ist abgelaufen: abgelehnt. Nach dem Zurücksetzen gelten weder das alte Passwort noch alte Sitzungen (Aufgabe 6).
5. Viele Anmeldeversuche von einer IP-Adresse: 429, andere Adressen spielen weiter, und ein gefälschter Header `X-Forwarded-For` hilft nicht (Aufgabe 5).
